05

Risks & gaps

2 gating · 3 refinements
R1
Order-book depth is unproven — and it's the ladder's whole point
Kalshi orderbook auth is documentation-conflicted → (probe) in §1; the app is unauthenticated by default. Without proven access the MD ladder is top-of-book only, not a real DOM. Gates the centrepiece.
R2
NiceGUI feasibility of the dense terminal shell
Today's UI is Quasar ui.table. Docking + command-line parser + amber grid + ladder is a substantial custom build and may trip §13's "dedicated front-end if NiceGUI blocks core UX" trigger. Validate one slice before full commit.
G3
Research appears twice
A blotter "Research" tab AND the RES surface. To honour §0.1 separation, keep research OFF the executable blotter — RES surface + card-attached evidence only.
G4
Default theme
Amber-on-black is the signature but can fatigue; the high-contrast toggle mitigates. Owner call below.
G5
Accessibility
Carry colourblind-safe, non-colour-only cues (icon+text) through to the rebuild (§9.3).
06

Recommended path

2 gates, then a 4-phase milestone
GATE A
Probe order-book depth (R1). Decide: real DOM vs labelled top-of-book preview. Gates the ladder.
GATE B
NiceGUI shell feasibility spike (R2). Build one real slice — amber theme + blotter grid + command line + one docked panel — or trigger the dedicated-front-end decision.
P1 · SHELL
Command line + status/trust strip + tiles + blotter from the real engine; full clickable nav (command line = accelerator, never required).
P2 · CARD
DES trade-card from real fields (legs/quote/EvidencePack); confidence only for dims that exist; $1⇄$100.
P3 · LADDER
MD ladder — gated on Gate A.
P4 · SURFACES
RES / OPS surfaces + alerts (roadmap-future; every metric behind §0.1 isolation tests).
